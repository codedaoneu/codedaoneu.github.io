# Tài liệu hướng dẫn sử dụng Cube Core

## 1. Cube Core là gì

Cube Core là một framework mã nguồn mở đóng vai trò "semantic layer" (headless BI) nằm giữa các nguồn dữ liệu (data warehouse, database) và các công cụ hiển thị (BI tool, dashboard, ứng dụng nội bộ). Nó cho phép định nghĩa một lần các khái niệm nghiệp vụ (đo lường, chiều phân tích, quan hệ) dưới dạng "cube", rồi phục vụ lại qua nhiều giao thức khác nhau: REST API, GraphQL API, SQL API (kết nối như một database ảo cho các công cụ BI như Tableau, Power BI, Looker Studio...).

Lợi ích cốt lõi: định nghĩa business logic một chỗ, dùng lại nhiều nơi, tránh việc mỗi team tự viết SQL khác nhau dẫn đến số liệu lệch nhau; đồng thời có cơ chế cache và pre-aggregation để tăng tốc truy vấn trên dữ liệu lớn.

## 2. Kiến trúc tổng quan (Architecture)

Cube Core gồm các thành phần chính vận hành cùng nhau: API Gateway (tiếp nhận request REST/GraphQL/SQL), Cube Store (kho lưu trữ pre-aggregation dạng columnar để tăng tốc), Cube Backend (xử lý logic, sinh SQL, quản lý cache), và kết nối tới Data Source (database/warehouse gốc). Khi một truy vấn được gửi lên, Cube sẽ kiểm tra xem có pre-aggregation phù hợp đã được build sẵn hay không; nếu có sẽ trả kết quả từ Cube Store (rất nhanh), nếu không sẽ sinh SQL và query trực tiếp xuống data source gốc (có thể chậm với bảng lớn).

Về triển khai và vận hành sản xuất (Deployment/Running in Production), tài liệu Cube Core đề cập tới các mô hình chạy: single instance, cluster (tách riêng API instance và refresh worker), cấu hình biến môi trường, kết nối nhiều data source, giám sát hiệu năng, và các khuyến nghị về resource/scaling. Đây là các nội dung dành cho đội hạ tầng/DevOps quản lý instance, không phải phần thao tác hàng ngày của Data Analyst.

## 3. Data Model thực tế trên instance semantic.gimo.vn

Instance hiện có 5 cube và 1 view:

- **dim_customer** — dữ liệu khách hàng, gồm dimension như gender, và measure count. Đây là cube nhẹ, truy vấn rất nhanh (đã có cache/pre-aggregation).
- **dim_date** — bảng ngày tháng dùng để join/phân tích theo thời gian.
- **dim_employee** — dữ liệu nhân viên.
- **dim_partner** — dữ liệu đối tác.
- **fact_daily_debt_snapshot** — bảng fact lớn, snapshot công nợ hàng ngày. Measures: count, overdue_day_number, total_disbursed_amount, total_fee_amount, total_request_amount. Dimensions: bill_code, collection_channel, created_at, updated_at, date, principal_due_date.
- **example_view** — một view mẫu gộp nhiều cube lại (chưa khám phá sâu).

Lưu ý quan trọng: fact_daily_debt_snapshot là bảng lớn và **chưa có pre-aggregation phù hợp** cho các truy vấn thử nghiệm, nên truy vấn trực tiếp trên đó rất chậm (xem mục 5).

## 4. Hướng dẫn từng bước sử dụng Playground cho Data Analyst

**Bước 1 — Khám phá Data Model:** Vào tab "Data Model" → "Files" để xem trực tiếp định nghĩa YAML của từng cube (đo lường, chiều, kiểu dữ liệu, join). Đây là cách nhanh nhất để hiểu cube nào có sẵn field gì trước khi query.

**Bước 2 — Xây dựng truy vấn tại tab Playground:** Ở sidebar bên trái, tìm cube cần dùng (có ô search), bấm mở rộng để thấy danh sách measures/dimensions, click vào field muốn thêm vào query. Có toggle "All members / Used only" để lọc hiển thị.

**Bước 3 — Thêm bộ lọc (Filters):** Có hai cách: (a) bấm "+ Add" trong panel Filters để chọn dimension/date-range từ đầu; (b) cách nhanh hơn là bấm icon filter nhỏ cạnh tên field ngay trong sidebar, chọn "Filter by This Member" hoặc "Filter by Date Range" — cách này tự động gán đúng field. Sau khi filter xuất hiện, cần chọn lại operator (mặc định là "is set", thường cần đổi thành "equals" hoặc tương đương) rồi nhập giá trị và nhấn Enter để filter có hiệu lực.

**Bước 4 — Chạy truy vấn và đọc kết quả:** Bấm "Run Query". Kết quả hiển thị dạng bảng (Table) mặc định; có thể đổi sang Bar/Line/các dạng chart khác. Với dữ liệu nhiều chiều, dùng "Pivot" để cấu hình field nào lên trục X, field nào lên trục Y.

**Bước 5 — Kiểm tra cách Cube sinh truy vấn:** Các tab kết quả phụ gồm "Generated SQL" (xem SQL thật được sinh ra chạy xuống data source), "SQL API", "REST API", "GraphQL API" (xem cách gọi cùng truy vấn đó qua từng giao thức) — rất hữu ích khi cần tích hợp vào BI tool hoặc ứng dụng khác.

**Bước 6 — Prototype chart nhanh:** Bấm nút "Code" để mở modal "Chart Prototyping", cho phép chọn framework (React/Vue/Angular...) và thư viện chart (Chart.js...), xem trước scaffold code tương ứng với query hiện tại.

**Bước 7 — Nhận biết gợi ý pre-aggregation:** Khi một truy vấn không được tăng tốc, Playground hiển thị cảnh báo dạng link "Query was not accelerated with pre-aggregation" → bấm vào sẽ mở "Rollup Designer" cho xem định nghĩa rollup gợi ý (dạng JavaScript hoặc YAML). Analyst có thể xem để hiểu vì sao chậm, nhưng **việc áp dụng (Add to Data Schema) vào data model thật cần có phê duyệt của người quản lý data model**, vì đây là thay đổi cấu hình production.

## 5. Ví dụ thực hành chi tiết (đã thực hiện trực tiếp trên instance)

**Ví dụ A — Truy vấn nhanh, có cache: đếm khách hàng theo giới tính**

Query: measure `dim_customer.count`, dimension `dim_customer.gender`. Kết quả trả về gần như tức thời:

| Giới tính | Số lượng |
|---|---|
| O | 213.603 |
| F | 115.708 |
| M | 98.896 |
| (NULL) | 38.325 |
| **Tổng** | **466.532** |

Đây là ví dụ minh họa cho truy vấn được cache/pre-aggregation tốt: chạy nhanh, phù hợp để demo hoặc dùng lặp lại nhiều lần trong dashboard.

**Ví dụ B — Thêm bộ lọc để kiểm tra chéo số liệu**

Từ Ví dụ A, thêm filter `dim_customer.gender equals "F"` (thao tác: bấm icon filter cạnh dimension gender → chọn "Filter by This Member" → đổi operator từ "is set" sang "equals" → gõ "F" → Enter → Run Query). Kết quả trả về đúng 1 dòng: gender = F, count = 115.708 — khớp chính xác với con số đã thấy trong bảng breakdown ở Ví dụ A. Đây là cách thực hành tốt để đối chiếu, xác minh số liệu trước khi đưa vào báo cáo.

**Ví dụ C — Truy vấn nặng trên bảng fact lớn, minh họa vì sao cần pre-aggregation**

Thử query trên `fact_daily_debt_snapshot`: measure `total_disbursed_amount`, dimension `collection_channel`, time dimension `date` (granularity: month). Kết quả: truy vấn treo hơn 40 giây không trả về kết quả. Thử thêm filter date range "Last quarter" cũng không cải thiện được tốc độ, phải bấm "Stop" để hủy.

Nguyên nhân (xác nhận qua "Query was not accelerated with pre-aggregation" và Rollup Designer): cube này chưa có pre-aggregation phù hợp cho tổ hợp measure + dimension + time-granularity đang truy vấn, nên Cube phải chạy SQL trực tiếp xuống database gốc trên một bảng snapshot hàng ngày rất lớn.

Bài học thực hành: với các bảng fact lớn, Analyst nên (1) kiểm tra tab Generated SQL / cảnh báo pre-aggregation trước khi chạy query rộng, (2) thu hẹp phạm vi bằng filter thời gian cụ thể thay vì quét toàn bộ lịch sử, (3) nếu truy vấn kiểu này sẽ dùng lặp lại thường xuyên, đề xuất với đội quản lý data model bổ sung pre-aggregation tương ứng (không tự ý bấm "Add to Data Schema" trên môi trường thật).

## 6. Các API tích hợp có sẵn (Frontend Integrations)

Instance cung cấp 3 endpoint chính: REST API, GraphQL API, và Websocket endpoint, cùng ví dụ lệnh curl mẫu cho từng loại. Với Data Analyst, cách dùng phổ biến nhất là **SQL API**: kết nối trực tiếp công cụ BI quen thuộc (Power BI, Tableau, DBeaver...) vào Cube như thể nó là một Postgres database, mà không cần viết code — mọi câu SQL gửi lên sẽ được Cube tự động dịch sang truy vấn xuống data source thật (và tận dụng pre-aggregation nếu có).

## 7. Lưu ý an toàn và giới hạn khi thao tác trên instance thật

Vì semantic.gimo.vn là instance thật đang phục vụ dữ liệu nghiệp vụ (khách hàng, công nợ) chứ không phải môi trường demo, trong quá trình thực hành đã chủ động tuân thủ các giới hạn sau: không áp dụng gợi ý pre-aggregation vào data model thật, không tải xuống bất kỳ file scaffold/code nào từ tính năng Chart Prototyping mà không có xác nhận trước, và ưu tiên dùng các measure/dimension tổng hợp (như đếm số lượng, gộp theo giới tính) thay vì truy xuất dữ liệu chi tiết từng cá nhân.
